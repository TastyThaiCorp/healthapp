# HealthUp regulatory research and launch decisions

Research date: **6 October 2026**. This is an engineering applicability assessment and implementation record, not legal advice, certification or an exhaustive worldwide legal opinion. A Colorado entity's obligations depend on its legal identity, users, marketing, data flows, scale, processors and intended claims. Those facts must be reviewed by qualified counsel before account/billing activation. Disclaimers and signatures do not provide blanket immunity or waive non-waivable rights.

## Data flow

Public frontend → device IndexedDB (AES-GCM). Device keys are non-extractable but usable by same-origin app code; unlocked-browser access and XSS remain risks. Account partitions prevent ordinary UI mixing, not forensic access by someone controlling the browser. Use device encryption/passcodes and clear local copies on shared devices.

Account registration → FastAPI → encrypted email/name/consent fields in a persistent SQLite volume. Passwords are Argon2id hashes. Opaque session/reset tokens are stored as hashes. Transactional emails contain links, not wellness records. Reset tokens are in URL fragments so they are not sent in the initial HTTP request.

Optional Plus backup → authenticated and CSRF-checked API → encrypted backup. The server holds the key: **not end-to-end encryption**. No routine wellness upload happens automatically. Withdrawal removes the primary backup; underlying host backup retention and contractual processor deletion remain operational duties.

Optional food/research search → server → USDA/NCBI. Only user-entered query terms, never automatic mood/journal data. Warn users against personal details in searches. Public-query cache is bounded. Stripe receives necessary account/payment context and a random user reference, not wellness fields. Fonts and wellness illustrations are self-hosted. No advertising or analytics SDKs are installed.

## Required operational decisions before production activation

- Name the legal operator and working privacy/support contact; finalize actual customer-facing notices and terms with counsel.
- Confirm adult-only US initial scope or separately assess any proposed additional region; do not interpret a country dropdown as verified geolocation.
- Maintain a data inventory, purpose/basis record, sensitivity/risk/DPIA assessment, processor agreements and international-transfer analysis where needed.
- Establish incident response, breach assessment/notification ownership, security monitoring without health payloads, secrets rotation and staff offboarding.
- Run deletion/withdrawal through actual hosting backup expiry, processors and payment-record retention; do not promise that code removes legal billing records from Stripe.
- Run the documented maintenance command daily and monitor failures; define unverified-account and inactivity retention, infrastructure backup expiry and legal holds before launch.
- Assign owners and statutory deadlines for privacy requests and appeals. Marking a queue status is not fulfillment of an underlying legal right.
- Configure email delivery, verified sender domain, billing cancellation/receipt/renewal notices, tax/refund/customer-support obligations, and independent security review.
- Treat accessibility and product safety as operational duties too; automated checks do not certify WCAG conformity on every device.

The `HEALTHUP_LEGAL_REVIEWED` and `BILLING_TERMS_REVIEWED` flags are activation configuration, **not legal certifications**. They must reflect actual operator review, not an assumption that this document settles every law.
